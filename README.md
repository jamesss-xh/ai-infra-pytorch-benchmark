# 基于 PyTorch 的 CPU 推理性能测试与批处理分析

## 1. 项目简介

本项目使用 PyTorch 构建一个小型多层感知机（MLP），在 Windows CPU 环境下测量前向推理性能，比较不同批次大小（batch size）与 PyTorch CPU 线程数对延迟和吞吐量的影响，并通过重复实验观察结果波动。

**项目定位：** AI Infra 入门级性能基准测试与配置分析。当前版本完成的是基准测试、数据记录和配置对比，**尚未实现自定义算子、底层 kernel 优化或真实大模型推理加速**。

## 2. 实验环境

根据实际环境检查与终端输出：

- 操作系统：Windows（终端输出 `Windows-10-10.0.26200-SP0`）
- Python：3.11.9
- Python 路径：`D:\python311\python.exe`
- PyTorch：2.11.0+cpu
- Matplotlib：3.10.9
- 设备：CPU
- CUDA：不可用；本项目不依赖 CUDA
- 默认 PyTorch CPU 线程数：16
- 模型：小型 MLP，输入维度 256、隐藏层维度 512、输出维度 10
- 输入：程序生成的随机合成数据，不是真实数据集，也不是大语言模型

## 3. 如何运行

在包含 `benchmark.py` 的项目目录中打开 PowerShell 或 VS Code 终端：

```powershell
python benchmark.py
```

默认配置：

- batch size：`1, 8, 32, 64`
- 预热次数：15
- 计时迭代次数：60
- CPU 线程数：16

自定义参数示例：

```powershell
python benchmark.py --batch-sizes 1 8 32 64 --threads 4 --warmup 50 --iterations 300
```

程序会在 `results/` 下生成 `benchmark_results.csv` 和三张图。每次运行会覆盖这些默认文件；若要保留某次实验，请在运行后立即复制并改名，例如：

```powershell
Copy-Item .\results\benchmark_results.csv .\results\my_run_threads4.csv
```

## 4. 指标定义

- **平均批次延迟（mean batch latency）**：一次模型前向计算处理整个 batch 的平均耗时，单位毫秒（ms）。
- **P95 批次延迟**：本轮单次测量延迟的第 95 百分位近似值。短时微基准中的 P95 容易受到系统调度和计时噪声影响。
- **吞吐量（samples/s）**：`batch_size / mean_batch_latency_seconds`，表示每秒处理的样本数。
- **平均每样本计算时间**：平均批次延迟除以 batch size。它是批次计算时间的平均分摊值，**不等于**真实服务中的单请求端到端响应延迟。
- 程序使用 `torch.inference_mode()` 执行推理，并将输出数值检查放在计时区间之外。

## 5. 实验一：不同 batch size（16 线程）

设置：预热 15 次，每个 batch size 计时 60 次。以下数据来自首次基准测试的真实终端输出。

| Batch size | 平均批次延迟 (ms) | P95 (ms) | 吞吐量 (samples/s) | 平均每样本计算时间 (ms) |
|---:|---:|---:|---:|---:|
| 1 | 0.0434 | 0.0623 | 23,067.16 | 0.0434 |
| 8 | 0.0494 | 0.0548 | 161,954.25 | 0.0062 |
| 32 | 0.1162 | 0.1669 | 275,490.00 | 0.0036 |
| 64 | 0.1695 | 0.2219 | 377,532.86 | 0.0026 |

**观察：** 在这次测试中，batch size 增大时，批次总延迟上升，吞吐量也上升，而平均每样本计算时间下降。这反映了当前模型与 CPU 微基准中的吞吐量—延迟权衡，不应直接推广到真实模型或生产服务。

## 6. 实验二：不同 CPU 线程数的单轮比较

设置：每个线程配置预热 15 次、计时 60 次。表格列出各配置实测吞吐量；该实验每个配置只有一轮，因此先作为探索性对比。

| Batch size | 1 线程 | 4 线程 | 8 线程 | 16 线程 | 本轮最高吞吐量配置 |
|---:|---:|---:|---:|---:|---|
| 1 | 24,602.26 | 28,800.46 | 27,877.15 | 23,067.16 | 4 线程 |
| 8 | 87,485.87 | 170,182.59 | 128,489.98 | 161,954.25 | 4 线程 |
| 32 | 132,600.35 | 296,873.55 | 419,837.31 | 275,490.00 | 8 线程 |
| 64 | 143,147.91 | 347,778.83 | 407,963.79 | 377,532.86 | 8 线程 |

单位：samples/s。

**观察：** 在这轮单次比较中，batch size 为 1 和 8 时，4 线程吞吐量最高；batch size 为 32 和 64 时，8 线程吞吐量最高。结果提示线程配置与批次大小之间存在交互影响；由于每个配置仅测量一轮，不能把这张表视为普遍最佳配置。

## 7. 实验三：重复比较 4 线程与 8 线程

设置：4 线程与 8 线程分别独立运行 3 次；每次预热 50 次、计时 300 次；batch size 为 1、8、32、64。表格中的“±”为三次运行吞吐量的样本标准差，不是置信区间。

| Batch size | 4 线程平均吞吐量 ± 标准差 (samples/s) | 8 线程平均吞吐量 ± 标准差 (samples/s) | 8 线程相对 4 线程变化 |
|---:|---:|---:|---:|
| 1 | 27,589.22 ± 241.79 | 27,341.64 ± 1,838.44 | -0.90% |
| 8 | 156,941.17 ± 7,499.64 | 163,127.24 ± 1,405.43 | +3.94% |
| 32 | 281,287.55 ± 10,662.58 | 440,793.46 ± 43,826.52 | +56.71% |
| 64 | 324,076.17 ± 4,519.72 | 573,335.57 ± 13,849.68 | +76.91% |

**观察：**

- Batch size 为 1 时，8 线程的平均吞吐量比 4 线程低约 0.90%，没有显示出收益。
- Batch size 为 8 时，8 线程的平均吞吐量高约 3.94%，差异较小。
- Batch size 为 32 和 64 时，8 线程的平均吞吐量分别高约 56.71% 和 76.91%。
- 当前重复实验支持一个有限结论：在本项目的小型 MLP 与 CPU 测试条件下，较大的 batch size 更可能从 8 线程配置中获益。但每种配置只有 3 次运行，仍需谨慎解释。

## 8. 额外验证运行

在整理项目时，又使用默认配置（16 线程、预热 15 次、计时 60 次）运行了一次。该次输出如下，单独记录，不与实验一的首次结果混合：

| Batch size | 平均批次延迟 (ms) | P95 (ms) | 吞吐量 (samples/s) | 平均每样本计算时间 (ms) |
|---:|---:|---:|---:|---:|
| 1 | 0.0411 | 0.0510 | 24,354.60 | 0.0411 |
| 8 | 0.0580 | 0.0704 | 137,986.55 | 0.0072 |
| 32 | 0.0924 | 0.1371 | 346,151.77 | 0.0029 |
| 64 | 0.1575 | 0.2441 | 406,396.51 | 0.0025 |

这次结果与首次 16 线程测试存在差异，说明短时微基准会受到运行环境、系统调度和其他噪声影响。比较配置时应优先采用同一实验方案下的重复运行结果，而不是挑选某一次较高的数字。

## 10. 局限性

1. 模型是小型 MLP，输入为随机合成数据，不代表真实大语言模型。
2. 测试仅涉及 CPU 前向推理，不涉及 GPU/NPU，也没有实现自定义算子或底层 kernel 优化。
3. 4 线程与 8 线程的重复实验各只有 3 次，统计结论仍有限。
4. 单次计算耗时很短，操作系统调度、CPU 电源状态和后台程序可能造成明显相对误差。
5. 吞吐量高不等于单个用户请求端到端响应更快；生产服务还要考虑排队、批处理等待、预处理、传输和并发负载。
6. 不同批次、线程实验应保持相同的模型、输入维度、预热和计时设置，才能做公平比较。

## 11. 结论与下一步

本项目完成了一个可运行的 PyTorch CPU 推理基准测试，比较了不同 batch size 和 CPU 线程配置，并对 4 线程与 8 线程开展了三次重复实验。当前实测数据表明，批次大小和线程数会影响吞吐量与延迟之间的权衡；较大的 batch size 在本次测试中更能受益于 8 线程，但该结论只适用于当前测试条件。

后续可选择一个变量继续研究，例如改变模型规模、扩大重复实验次数，或使用真实模型与明确的请求负载进行测试。每轮实验应保留原始数据、写明运行参数，并基于实际结果判断优化是否有效。
